# MewAgent v0.2 执行手册（playbook）

> 用途：v0.2 开发是**单人 + 单模型**执行。本文件规定"一个 task 怎么从开工走到合并"，避免会话一换就丢上下文、避免 AI 一次改太多。
> 配套：[plan.md](./plan.md)（为什么做）、[tasks.md](./tasks.md)（做什么）、[testing.md](./testing.md)（怎么验）。
> 若将来改成多模型/多人并行，先写 ADR 并修订本文件；不要在执行中悄悄改变分工方式。

---

## 1. 三条硬规则

1. **一次会话只做一个 task**。开工前把 task id 写在会话第一行；跨 task 的改动先拆分。
2. **先计划、后动手**。AI 先给出"要改哪些文件、加哪些测试、有什么风险"的计划，人确认后再写代码。
3. **没有证据不算完成**。A 级测试输出 + B 级手工记录 + 文档更新，三者缺一不可。

---

## 2. 会话生命周期

### 2.1 开工前核对（2 分钟）

```powershell
cd D:\workplace\AIAgent\MewCode
git status --short          # 必须干净；有改动先处理
git switch main
git pull
git log --oneline -3        # 确认基线
npm test                    # 可选，慢；至少确认上次全绿
```

然后在会话里贴开场提示词（§6.1）。

### 2.2 会话中

- 开工：把 `docs/v0.2/tasks.md` 对应 task 置 `doing`，HANDOFF §7 记一行"会话 N 开工 V2-x-y"。
- 每完成一个可验证的小步：typecheck + 相关测试，再继续；不要攒一大坨 diff。
- 遇到契约变更（`src/types.ts`、`CompressResult`、session schema）：停下来，更新 plan §5/§6 并在会话里说明，得到确认再改。
- 遇到范围外需求：记到 tasks.md"计划外任务"或 v0.3 候选，不顺手做。

### 2.3 收尾（必须做）

1. `npm run typecheck`、`npm test`、`npm run build` 全绿。
2. 按 testing.md 对应 task 跑 A 级；B 级列清单等用户做（不要冒充已做）。
3. 更新 `tasks.md`（状态 + 证据）、`HANDOFF.md` §7（会话记录 + 提交哈希）、必要时 README/docs 索引。
4. 提交、推送、开 PR（单人也要走 PR，留下可回滚的记录）。
5. 会话结束前给一段"下一会话从这里开始"的交接摘要。

## 3. 分支、提交与 tag

### 3.1 分支

| 用途 | 命名 | 从哪来 | 合并方式 |
|---|---|---|---|
| 单个 task | `v2/<task-id>-<slug>`，如 `v2/V2-1-2-summary-strategy` | `main` | PR → squash |
| 阶段验收/发布 | `release/v0.2.x`（可选） | `main` | 只打 tag，不改代码 |
| 紧急热修 | `hotfix/<slug>` | 对应 tag/`main` | PR → squash |

- 一个分支只服务一个 task；不要在一个分支里夹带下一个 task。
- 合并后删远端分支；本地可留。
- 需要并行两个 task 时用 `git worktree` 放到 `../MewAgent-v2-<task-id>`，各自独立 `npm install`；不要在同一工作区切分支跑两个会话。

### 3.2 提交信息

```text
<type>(<scope>): <中文摘要，≤50 字>

<可选：为什么这么做、影响范围>
```

- type：`feat` / `fix` / `test` / `docs` / `refactor` / `chore`。
- scope：`compress`、`session`、`slash`、`mcp`、`publish`、`ui`、`agent`。
- 一个提交只做一件事；测试和实现可以同提交，但不要"顺手格式化整个文件"。
- 禁止把 `.env`、临时脚本、测试沙盒数据提交进仓库。

### 3.3 tag

| tag | 时机 |
|---|---|
| `v0.2-s1` … `v0.2-s4` | 每个阶段验收通过后 |
| `v0.2.0` | npm 发布提交 + checklist 全绿 |
| `v0.1.0-final` | 已存在，**不要移动**（回滚锚点） |

打 tag 前必须跑 testing.md §4 的阶段回归，并在 HANDOFF §7 记录。

## 4. 一个 task 的标准循环

```text
读（plan/tasks/testing/相关源码）
→ 写计划（改哪些文件、测试、风险）
→ 人确认
→ 小步实现 + 小步测试
→ A 级全跑
→ B 级清单交给用户
→ 更新文档（tasks/HANDOFF/README）
→ commit → push → PR → squash
→ 下一 task
```

每步的"完成定义"（DoD）：

- [ ] 代码符合 `src/types.ts` 契约，没有 `any` 逃逸（v0.1 的红线保持）。
- [ ] 新行为有 A 级测试；修 bug 有回归用例。
- [ ] `typecheck` / `test` / `build` 全 0。
- [ ] 错误信息符合"发生了什么 + 下一步"（v0.1 `errors.ts` 风格）。
- [ ] 文档同步：tasks 状态、HANDOFF §7、README/索引（若用户可见行为变了）。
- [ ] 没有提交密钥、临时文件、测试数据。

## 5. 自审清单（提 PR 前自己过一遍）

| 检查 | 问题 |
|---|---|
| 范围 | 是否只改了本 task 需要的文件？有没有"顺手优化"？ |
| 契约 | 是否改了 `types.ts`/session schema/CLI 参数？有没有更新 plan 与测试？ |
| 错误路径 | 失败时用户看到什么？是否可行动？会不会崩？ |
| 兼容 | v0.1 的会话/配置/参数还能用吗？迁移是否保留备份？ |
| 安全 | 新代码是否绕过 gate？MCP 是否默认信任了第三方？ |
| 资源 | 是否有未关闭的 socket/子进程/定时器？abort 是否传播？ |
| 测试 | A 级覆盖正常/边界/失败；B 级是否列清楚？ |
| 文档 | 下一个会话不看聊天记录，能否只靠文档接手？ |

## 6. 提示词模板

### 6.1 新会话开场（复制后只改 task id）

```text
你是 MewAgent 项目的开发助手。本次会话只做一个 task：<V2-x-y 名称>。

开工前请按顺序读：
1. HANDOFF.md（当前状态与上一会话交接）
2. docs/v0.2/plan.md（目标、范围、关键决策）
3. docs/v0.2/tasks.md 中 <V2-x-y> 一行与依赖
4. docs/v0.2/testing.md 中 <V2-x-y> 一节
5. docs/v0.2/playbook.md（执行规则）
6. AGENTS.md（仓库红线）

然后：
- 核对 git status 干净、当前分支、基线测试数；
- 给出实现计划（文件、测试、风险、预计时长），等我确认后再写代码；
- 只做这一个 task，不改契约/不加范围外功能；需要改契约先停下来告诉我；
- 完成后跑 typecheck/test/build，贴 A 级结果；B 级列清单等我做；
- 更新 tasks.md 状态、HANDOFF §7，并给出提交信息。
```

### 6.2 实现一个子步骤

```text
只实现 <子步骤>，不要动其它文件。要求：
- 输入/输出契约：<贴类型或函数签名>
- 错误处理：失败时返回/抛出什么，用户看到什么
- 先写测试（或同时写），测试文件 <路径>
- 完成后跑 <命令>，贴输出摘要
```

### 6.3 修 bug

```text
现象：<复现步骤>
预期：<...>
实际：<...>
请先复现并定位根因，不要直接改。给出：根因、最小修复方案、回归测试用例；
我确认后再改。修完跑 <测试命令>，并确认没有引入新失败。
```

### 6.4 评审一个 diff

```text
请按 docs/v0.2/playbook.md §5 自审清单评审当前 diff：
范围、契约、错误路径、兼容、安全、资源、测试、文档。
只列问题与建议，不要直接改；按 P0/P1/P2 分级。
```

### 6.5 会话收尾

```text
收尾：更新 docs/v0.2/tasks.md 的 <V2-x-y> 状态与证据、
HANDOFF.md §7 会话记录（时间、task、提交哈希、B 级待办）、
必要时 README/索引；给出提交信息与下一会话建议。
```

## 7. 停止条件（遇到就停，不要硬推）

- 需要改 `src/types.ts` 契约或 session schema，但 plan 没写：先更新 plan。
- A 级测试连续 3 次修不好：保留复现，写 blocked，换思路或求助。
- 发现 v0.1 行为被破坏：立即停，先补回归用例。
- MCP server 出现不可控副作用（删文件/联网）：关掉 server，记录，评估是否只读模式。
- 发布相关（npm 登录、2FA、包名）：必须用户本人操作，AI 不代做。
- 同一个错误反复出现且没有新信息：停，写清"已试过什么、卡在哪"。

## 8. 回滚与恢复

| 场景 | 操作 |
|---|---|
| 单 task 改坏 | `git reset --hard` 到分支起点；或 `git revert` 已合并提交 |
| 阶段验收失败 | 回到阶段 tag（`v0.2-s*`）继续修，不要带着问题进下一阶段 |
| v0.2 整体回滚 | `git reset --hard v0.1.0-final`；会话数据从 `.mewcode/session.json.bak` 恢复（见 [../rollback.md](../rollback.md)） |
| 会话文件损坏 | 不删原文件；先复制备份，再用 `--list`/索引重建；最坏丢弃单个会话 |
| npm 发布事故 | 72h 内 `npm unpublish`；否则 `npm deprecate` + 尽快 0.2.1 |

## 9. 常见失败模式（v0.1 教训 + v0.2 预判）

| 模式 | 表现 | 预防 |
|---|---|---|
| 一次性大 diff | 测试红一片、定位困难 | 小步提交；每步跑相关测试 |
| 契约偷偷改 | UI/loop/测试同时崩 | 改 `types.ts` 前停下来确认 |
| 只写代码不写测试 | A 级覆盖不到边界 | task 的验收先写测试 |
| B 级冒充已做 | 发布后才发现 IME/真实 API 问题 | 没做就写"待用户"，不写"通过" |
| 摘要每轮重复调用 | 费用涨、延迟高 | 摘要落盘 + 记录调用次数 |
| 迁移没备份 | 旧会话丢 | 先 `.bak`，失败不删源 |
| MCP 子进程残留 | 退出后 node 进程还在 | 统一 close；测试检查进程 |
| 代理/网络误判 | git push、npm 失败 | 先测 7890；失败信息贴全 |
| Windows 编码 | 中文乱码/CRLF 变化 | UTF-8 读写；测试覆盖 CRLF |
| 范围蔓延 | 阶段延期 | 非目标清单 + "计划外任务" |

## 11. FAQ

**Q：可以一个会话做两个小 task 吗？**
不建议。若两个 task 共享一个上下文且都很小（<30 分钟），可以合并，但要在 tasks.md 里分别标 done，并各自有测试证据。

**Q：AI 说"测试通过"但没贴输出？**
要求补命令与输出摘要；没有证据按未通过处理。

**Q：可以不更新 HANDOFF 吗？**
不行。HANDOFF 是下一会话唯一的入口；漏更新等于把成本转嫁给未来的自己。

**Q：分支可以直接 push main 吗？**
只有纯文档/一行配置允许直接 main（沿用 AGENTS.md）；功能改动必须走分支 + PR。
